# План обучения и выпуска Investment Ledger

Актуально на 10 августа 2026 года.

## Цель и границы

У плана две обязательные цели:

1. К **30 ноября 2026 года** выпустить `v1.0.0` инвестиционного ledger и уметь объяснить каждое существенное решение без подсказки.
2. Восстановить понимание ShareTrip настолько, чтобы без редактора провести один use case через transport, application, repository, storage и эксплуатационные механизмы, а также объяснить отличие его решений от Investment Ledger.

Это реалистичная цель уровня сильного junior/junior+ Go backend, а не попытка формально закрыть весь стек middle-разработчика за четыре месяца.

План рассчитан примерно на 10–12 часов в неделю. Если времени меньше, уменьшается необязательный scope, но не качество обязательных сценариев.

Контрольные даты:

- **16 августа** — проверены доменные инварианты и критерии Must/Should/Could backlog;
- **27 сентября** — работает in-memory HTTP API;
- **18 октября** — API работает с PostgreSQL и проходит smoke test в раннем staging;
- **1 ноября** — закрыты согласованность, конкурентность и идемпотентность;
- **15 ноября** — feature freeze;
- **23 ноября** — публичное окружение и полностью воспроизводимый запуск;
- **30 ноября** — тег `v1.0.0` и готовый демонстрационный сценарий;
- **1–20 декабря** — интервью, отклики и только небольшие исправления.

Fallback-гейты защищают дату релиза:

- если in-memory API опаздывает более чем на неделю к 27 сентября, все Could-labs сразу переносятся в декабрь;
- если PostgreSQL, четыре Must-операции или идемпотентность не зелёные к 18 октября, весь Should-scope переносится после `v1.0`;
- после 1 ноября новые доменные функции запрещены: остаются production readiness, исправления и релиз.

Минимальный релизный срез неизменен: Portfolio/Account/Instrument, четыре Must-операции, вычисляемые cash/position/average cost/current P&L, ручная последняя котировка, текущая summary, идемпотентный HTTP API, PostgreSQL, тесты, Docker/CI, health checks и документация запуска.

## Продукт v1.0

### Основные сущности

- `Portfolio` — портфель и его базовая валюта;
- `Account` — брокерский или денежный счёт;
- `Instrument` — тикер, тип и валюта инструмента;
- `Operation` — Must: пополнение, вывод, покупка и продажа; Should: дивиденд и комиссия;
- `Quote` — цена инструмента на момент времени;
- `Position` — вычисляемое состояние, а не редактируемая запись;
- `PortfolioSummary` — вычисляемые cash balance, market value, total value и unrealized P&L.

### Must — блокирует v1.0

1. Создать портфель, счёт и инструмент.
2. Записать неизменяемое пополнение, вывод, покупку или продажу.
3. Получить операции с пагинацией.
4. Рассчитать cash balance, количество, среднюю стоимость, market/total value и нереализованный P&L.
5. Вручную добавить котировку.
6. Получить сводку текущего состояния портфеля.
7. Безопасно повторить `POST` с тем же idempotency key.
8. Поднять API и PostgreSQL одной документированной командой.
9. Загрузить безопасные демонстрационные данные без реальных финансовых сведений.
10. Оставить demo-чтение публичным, а операции записи защитить API key.

### Should — только после зелёного Must

- дивиденды и комиссии;
- историческая сводка `as_of`;
- исправление ошибочной записи compensating operation без изменения истории;
- расширенные фильтры списка операций;
- сохранённый и документированный нагрузочный baseline.

### Could — timeboxed labs, не блокирует релиз

- CSV-импорт и fuzzing парсера;
- сравнение Fiber со стандартной библиотекой;
- оконные SQL-функции;
- transactional outbox;
- tracing через OpenTelemetry;
- углублённый `pprof` и escape analysis;
- gRPC/Proto adapter;
- внешний источник котировок за feature flag.

### Доменные ограничения

- Операции — source of truth; cash balance, позиции и сводка всегда вычисляются.
- Покупка или вывод не может сделать cash balance отрицательным.
- В первой версии поддерживается одна базовая валюта.
- Валюта инструмента, котировки и операции должна совпадать с базовой валютой портфеля.
- Для денег запрещён `float64`; масштаб и правила округления фиксируются явно.
- Количество и цена имеют документированную точность.
- Время хранится в UTC, правило `as_of` описывается в API.
- Продажа не может сделать позицию отрицательной.
- Повтор запроса не должен создавать вторую операцию.
- Записанная операция не обновляется и не удаляется.
- Любой экспериментальный snapshot или projection должен полностью перестраиваться из операций.

### Решения, которые фиксируются в ADR до 16 августа

- Cash balance: пополнения и продажи увеличивают остаток, выводы и покупки уменьшают его; дивиденды и комиссии добавляются к этой формуле только в Should-scope.
- Average cost: weighted average пересчитывается при покупке, не меняется при частичной продаже и обнуляется при закрытии позиции.
- Total value: cash balance плюс сумма `quantity * quote`; unrealized P&L считается относительно average cost открытой позиции.
- Для Should-режима `as_of` учитываются операции с `occurred_at <= as_of`; одинаковое время разрешается стабильным sequence, назначенным при append.
- Quote: для текущей сводки берётся последняя котировка, а для Should-режима — последняя с `quoted_at <= as_of`; отсутствие котировки для открытой позиции возвращает явную ошибку со списком тикеров.
- Fees в Should-scope хранятся отдельной cash-операцией и в `v1.0` не меняют cost basis; это осознанное упрощение.
- Should-reversal хранит уникальный `reverses_operation_id`, действует со своим `occurred_at` и компенсирует исходную операцию, не удаляя её. До reversal история показывает исходную операцию, после — обе; reversal отклоняется, если replay нарушит cash/position-инвариант.
- Idempotency key отличается от `OperationID` и имеет scope `API key + endpoint`; тот же key и payload возвращает сохранённые status/body, а тот же key с другим payload даёт `409 Conflict`. Key, fingerprint, ответ и операция сохраняются атомарно.

### Не входит до релиза

- брокерские интеграции, секреты брокера и реальные сделки;
- realtime market data;
- налоги, tax lots, split и другие корпоративные действия;
- мультивалютные портфели и любая FX-конвертация;
- регистрация пользователей и полноценная ролевая модель;
- расходы, категории и месячные бюджеты;
- frontend;
- микросервисы, Kafka, Kubernetes и service mesh.

## Как проходит каждый урок

1. Воспроизвести предыдущую тему по памяти.
2. Сформулировать одну новую идею простыми словами.
3. Получить небольшое условие и критерии приёмки.
4. Сделать самостоятельную попытку.
5. Запустить код и разобрать результат или ошибку.
6. Добавить тест либо другую воспроизводимую проверку.
7. Выполнить `gofmt`, `go vet` и `go test`; для конкурентного кода — `go test -race`.
8. Сделать self-review и один небольшой осмысленный коммит.
9. Записать, что теперь получается повторить без подсказки.

Подсказки выдаются ступенчато: наводящий вопрос → схема или псевдокод → ревью попытки → готовый фрагмент только последним шагом.

Все пункты без пометки блокируют контрольную работу этапа. Пункты с пометкой **lab** ограничены одной-двумя учебными сессиями и не блокируют `v1.0`: незавершённый lab переносится в декабрь. К таким темам относятся CSV/fuzzing, сравнение Fiber, оконные функции, outbox, OpenTelemetry, углублённый `pprof` и gRPC.

Недельный ритм при 10–12 часах:

- 1,5 часа — теория, воспроизведение по памяти и чтение соответствующего участка ShareTrip;
- 1,5 часа — маленькие изолированные упражнения;
- 5 часов — вертикальная функциональность проекта;
- 2 часа — тесты, рефакторинг, self-review и короткая запись сопоставления со ShareTrip;
- 1–2 часа — SQL, алгоритмы и вопросы для интервью.

## Обязательный параллельный трек ShareTrip

ShareTrip не является источником готового кода. Его задача — восстановить навык чтения существующего production-like проекта и связать изучаемую тему с реальной цепочкой вызовов. Разбор идёт от одного пользовательского сценария наружу, а не попыткой прочитать весь репозиторий подряд.

| После этапа | Что восстановить в ShareTrip | Артефакт понимания |
|---|---|---|
| 1–2. Язык и ошибки | Доменные типы, создание значений, валидация, путь и классификация ошибки | Краткий glossary и error-flow |
| 3. Пакеты и интерфейсы | Границы пакетов, направление зависимостей, интерфейсы, DI и тестовые doubles | Схема пакетов и список зависимостей выбранного use case |
| 4. HTTP и сети | Маршрут, handler, DTO, middleware, context и отображение ошибок в ответ | Sequence выбранного HTTP-запроса |
| 5. PostgreSQL | Repository, PGX, SQL, миграции и граница транзакции | Data-flow до таблиц и обратно |
| 6. Конкурентность | Goroutines, отмена, синхронизация, фоновые задачи или явное отсутствие этих механизмов | Список владельцев состояния и рисков race/leak |
| 7. Эксплуатация | Конфигурация, logs, metrics, health checks и graceful shutdown | Карта запуска и наблюдаемости |
| 8. Релиз | Полная цепочка одного use case и сравнение решений двух проектов | `docs/sharetrip-recovery.md` и устное объяснение на 5 минут |

Если соответствующего механизма в ShareTrip нет, это фиксируется явно: что отсутствует, нужно ли оно проекту и как аналогичная задача решена в Investment Ledger.

Контрольная работа: пакеты domain/application/memory создают `Portfolio`, `Account` и `Instrument`, записывают четыре Must-типа операций и вычисляют cash balance, позиции, average cost и P&L без HTTP, глобального состояния и инфраструктурных зависимостей.

1. `net/http`, жизненный цикл запроса и HTTP semantics.
2. REST-ресурсы, JSON DTO и преобразование в доменную модель.
3. Status codes и единый формат ошибок API.
4. `context.Context`, deadlines, timeouts и graceful shutdown.

## Этап 5. PostgreSQL и согласованность — 28 сентября – 18 октября

1. Реляционная модель, ключи, ограничения и нормализация.
2. DDL/DML, `JOIN`, `GROUP BY`, CTE; **lab:** оконные функции.
3. Миграции, PGX pool и точное SQL-отображение финансовых типов.
4. Repository adapter и отображение ошибок БД в доменные ошибки.
5. Интеграционные тесты на реальной PostgreSQL.
6. Транзакции, уровни изоляции, locks и deadlocks.
7. Атомарная проверка cash/position-инварианта и append операции без сохранения позиции как source of truth.
8. Idempotency: fingerprint и сохранённый ответ в одной транзакции с операцией; unique constraint остаётся последней защитой.
9. Индексы, `EXPLAIN (ANALYZE, BUFFERS)` и осмысленная оптимизация.
10. Seed data, ранний staging deploy и smoke test основного HTTP-сценария.

Контрольная работа: миграции поднимают пустую БД и Must-сценарии переживают рестарт; одинаковый key/payload воспроизводит исходный ответ, другой payload получает conflict, а конкурентная продажа не делает позицию отрицательной. Если выполнены Should-reversal или исторический `as_of`, для них добавляются отдельные integration tests.

## Декабрь. Выход на рынок — 1–20 декабря

- 5–10 целевых откликов в неделю с адаптацией резюме.
- Два mock-интервью в неделю и журнал ошибок.
- Повторение Go, SQL, HTTP, конкурентности и архитектурных решений проекта.
- Исправление только найденных дефектов и документации.
- gRPC, Redis или брокер сообщений добавляются отдельным маленьким lab, но не ломают `v1.0`.

## Параллельный трек для трудоустройства

Он идёт каждую неделю и не должен вытесняться разработкой продукта.

Темы ротируются, а не выполняются все в одну неделю: Git и Linux входят в проектные часы, SQL чередуется с алгоритмами, English summary пишется на milestone, system design начинается после готового HTTP API.

- Git: ветки, небольшие PR, rebase/merge, разрешение конфликтов и self-review.
- Linux/CLI: процессы, сигналы, env, права, порты, `curl` и чтение логов.
- Алгоритмы: Big O, array/hash map, stack/queue, поиск, сортировка, tree/BFS/DFS — одна задача в неделю, с ноября две.
- SQL: один-два запроса в неделю, включая JOIN, агрегацию и анализ плана.
- Английский: чтение первичной документации и короткий English summary каждого milestone.
- Интервью: пять вопросов по завершённому этапу с ответом без редактора.
- System design: монолит, cache, queue, consistency и horizontal scaling только после работающего API.

Generics достаточно изучить отдельным упражнением и не внедрять искусственно. Reflection нужно понимать на уровне JSON, struct tags и цены динамики. Redis, Kafka/RabbitMQ/NATS и Kubernetes полезны следующим слоем, но не должны вытеснить качественный монолит из ноябрьского релиза.

Дополнительно включены темы, которые регулярно встречаются в Go backend-задачах: concurrency и race detector, глубокий SQL, идемпотентность, безопасность, Docker/CI, наблюдаемость, профилирование, деплой, алгоритмы и интервью-подготовка.

Публичные источники программы: [страница программ Job4j](https://job4j.ru/programs) и [peterarsentev/job4j_go_lang_base](https://github.com/peterarsentev/job4j_go_lang_base). Подробная последовательность закрытых заданий недоступна, поэтому сопоставление ограничено публичными темами. Состав требований рынка нужно перепроверять перед декабрьскими откликами; этот план зафиксирован по доступным junior Go-вакансиям на 10 августа 2026 года.

Проверка приоритетов по рынку не является статистическим исследованием, но свежие примеры [Junior Golang](https://hh.ru/vacancy/129638662), [Junior Golang без обязательного опыта](https://hh.ru/vacancy/129284065) и текущая [лента Go-вакансий на Хабр Карьере](https://career.habr.com/vacancies/go_razrabotchik) повторяют ядро плана: Go/stdlib, HTTP/REST, SQL/PostgreSQL, concurrency, тесты, Git/Linux и Docker; gRPC, Redis, брокеры и Kubernetes образуют следующий слой.

## Тема считается усвоенной, если

- её можно объяснить без открытого кода;
- уменьшенный пример получается написать самостоятельно;
- понятно, кто вызывает функцию и что она возвращает;
- можно предсказать, в каком месте возникнет ошибка;
- есть тест или воспроизводимая проверка ожидаемого поведения;
- понятен компромисс и причина применения темы именно здесь.

## Definition of Done для v1.0

- Чистый checkout запускается по README.
- Миграции поднимают пустую PostgreSQL, seed создаёт только безопасные данные.
- Все бизнес-инварианты имеют unit tests.
- Ключевые repository/use case сценарии имеют integration tests.
- Есть E2E happy path и конкурентный конфликтный сценарий.
- Тот же idempotency key и payload воспроизводит исходный ответ без дубликата; другой payload с тем же key получает conflict.
- Конкурентные продажи не делают позицию отрицательной.
- `gofmt`, vet/lint, тесты, race detector и vulnerability scan проходят в CI.
- Сервис корректно завершается по сигналу.
- Есть request ID, structured logs, health/readiness и полезные метрики.
- Опубликованы OpenAPI, схема архитектуры, ADR и ограничения модели.
- Есть live demo или видео, локальный fallback и тег `v1.0.0`.
- `docs/sharetrip-recovery.md` проводит один use case ShareTrip от входа до данных и наблюдаемости, содержит схему зависимостей и сравнение с Investment Ledger.
- Автор объясняет отказ от `float64`, append-only ledger, идемпотентность, isolation level, placement интерфейсов, context cancellation и выбранный индекс.
- Автор без редактора объясняет выбранный use case ShareTrip, путь ошибки и границу транзакции.

## Если график начинает срываться

Scope уменьшается в таком порядке:

1. Не начинать или перенести в декабрь все Could-labs: внешний provider, gRPC, OpenTelemetry, outbox, Fiber, CSV/fuzzing и углублённый `pprof`.
2. Убрать Should-фильтры.
3. Убрать Should-reversal.
4. Убрать Should-режим исторического `as_of`.
5. Убрать Should-операции dividend и fee.
6. Убрать Should-нагрузочный baseline, сохранив обычный smoke test.

Нельзя вырезать: корректную денежную модель, cash/position/P&L расчёты, четыре Must-операции, PostgreSQL migrations, unit/integration tests, полную семантику идемпотентности, конкурентную защиту, Docker/CI, health checks, документацию запуска и демонстрационный сценарий.
