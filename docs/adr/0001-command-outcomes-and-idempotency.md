# ADR-0001: Результаты команды, повторы и компенсация

- Статус: принято для S02
- Дата: 2026-08-15

## Контекст

Клиент может не получить ответ после отправки `RecordOperationCommand` и не знать, были ли операции добавлены. Одна команда также может атомарно создать несколько операций, например покупку и комиссию. Поэтому `OperationID` недостаточно для распознавания повторной доставки команды.

Нужно различать четыре ситуации, которые требуют разного поведения: business rejection, technical failure, повторную доставку уже обработанной команды и исправление ранее принятого финансового факта.

## Решение

### Идентификаторы

- Клиентская программа создаёт `IdempotencyKey` до первой отправки логической команды. Пользователь не вводит ключ вручную.
- Автоматические повторы одной команды используют тот же `IdempotencyKey`.
- Новое осознанное действие пользователя получает новый `IdempotencyKey`, даже если payload совпадает с предыдущим.
- Investment Ledger создаёт отдельный `OperationID` для каждого принятого финансового факта.
- Один `IdempotencyKey` может быть связан с несколькими `OperationID`.

### Результаты обработки

| Ситуация | Классификация | Изменение журнала операций | Последующее действие |
|---|---|---|---|
| Зарегистрированная команда нарушает доменную validation или финансовый инвариант | Business rejection | Операции не добавляются | Терминальный отказ сохраняется для логической команды; повтор того же ключа и payload возвращает тот же отказ |
| Обработка не получила надёжного терминального результата из-за временного сбоя | Technical failure | Журнал не изменён либо результат append неизвестен клиенту | Клиент повторяет тот же payload с тем же ключом |
| Терминальный результат уже сохранён, но команда доставлена повторно | Повторная доставка | Журнал повторно не изменяется | Система возвращает сохранённый успех или business rejection |
| В принятом финансовом факте позднее обнаружена ошибка | Compensating operation | Добавляется новая связанная операция | Исходная операция остаётся неизменяемой; исправление является новой командой с новым ключом |

Одинаковый `IdempotencyKey` с другим payload возвращает conflict и не изменяет журнал. Payload используется для проверки идентичности команды, но не становится частью самого ключа.

Запрос, из которого нельзя прочитать корректный envelope и пригодный `IdempotencyKey`, отклоняется до регистрации логической команды. После этой входной проверки ключ и fingerprint проверяются или резервируются раньше доменной validation, чтобы любой терминальный результат команды можно было безопасно воспроизвести.

Business rejection является терминальным результатом конкретной логической команды. Если состояние портфеля позднее изменилось и пользователь хочет повторить бизнес-действие, клиент создаёт новый ключ. Старый автоматический retry не должен превратить сохранённый отказ в неожиданную покупку.

Успешный append операций, привязка `IdempotencyKey` к fingerprint payload и сохранение терминального результата должны происходить атомарно. Иначе между записью операции и записью результата возникнет окно для дубля.

## Последствия

- Просмотр списка операций остаётся полезным способом диагностики, но корректность повторов не зависит от ручной проверки пользователем.
- Клиент должен хранить ключ до получения терминального результата и отличать автоматический retry от нового действия пользователя.
- Серверу понадобится хранилище связи `IdempotencyKey` → fingerprint payload → терминальный результат → созданные `OperationID`.
- Точный формат ключа, алгоритм fingerprint, срок хранения результата и внешний HTTP-контракт будут определены на этапах реализации и API без изменения зафиксированной семантики.

## Отклонённые варианты

- Использовать `OperationID` как идентификатор повтора: одна команда может создать несколько операций.
- Создавать ключ на сервере после получения команды: при потере ответа клиент не узнает ключ для безопасного retry.
- Повторять неоднозначный запрос с новым ключом: обе доставки могут быть приняты как разные команды.
- Повторно вычислять сохранённый business rejection после изменения состояния: задержанный retry может выполнить действие без нового намерения пользователя.
- Изменять или удалять ошибочную принятую операцию: это разрушает append-only журнал и воспроизводимость расчётов.
